## Change under review

The native DeepSeek Harness may contribute to bounded real EMR4 development
without another generic qualification programme. The earlier unchanged-runner
requirement is replaced by one small task-coupled adapter allowance. The
broker, effective-tool, path, credential, retry, data and protected boundaries
do not relax.

## New or changed threats

| Threat | Consequence | Required control |
|---|---|---|
| Treating a preset as a tool-security boundary | The stock runner advertises tools outside the work order and the broker rejects or, if weakened, over-admits the request | Keep the exact three-tool broker; use stock headless only to HMR-load the custom runner; verify effective tools before provider I/O |
| Using the adapter allowance as a new Harness programme | Real development stalls behind further runner archaeology | Limit the allowance to one small reusable runner/coordinator module plus one focused deterministic test inside the real task; otherwise end the native lane |
| Broadening the broker to make the stock runner pass | Shell/write/image/plan tools could reach the model outside the admitted contract | Never broaden the broker for task compatibility; narrow the runner instead |
| Letting Harness events write canonical clockwork state | Partial or malformed agent events could corrupt governance time | Broker and worker emit evidence only; Sol supplies three typed boundary readings to the exclusive clockwork publisher |
| Expanding clockwork vocabulary for every Harness event | Closed-vocabulary lapses and repeated closeout reruns increase | Keep a small coarse boundary vocabulary and retain detailed diagnostics outside canonical state |
| Mistaking transport attribution for model reliability | Native Harness could be promoted without useful accepted work | Record useful candidate and task completion separately from trace completeness |
| Silent recovery through Claude Code | Transport performance and provenance become untraceable again | Require explicit recovery provenance and a fresh allocation for any non-Sol transport |
| Retaining raw model or credential material | Repository evidence could expose prompts, reasoning, data or secrets | Persist sanitized structural readings only; remove raw sessions and disposable roots after Sol review |
| Reusing a stale task envelope | DeepSeek edits against the wrong source or path authority | Bind a fresh sparse worktree, full 40-character source object, work order and owned paths before every dispatch |
| Treating an accepted worker diff as accepted product authority | Default-off admission or another product surface could move without Sol judgment | DeepSeek produces a candidate only; Sol owns API meaning, tests, integration and acceptance |

## Residual risk accepted for monitored use

The adapter may still fail before DeepSeek receives the packet, and DeepSeek
may produce no useful candidate after receiving it. Those are acceptable
secondary-worker risks because the task remains reversible, the broker fails
closed, Sol can complete the development work, and the terminal is attributable.
They do not justify provider, data, deployment or protected-ref authority.

## Unchanged closed surfaces

No live database, Docker, secret resolution, operational environment,
product/patient/clinical data, ordinary-practice enablement, feature-flag or
allowlist change, command mounting, generic-status `Arrived`, action grammar,
waiting-area movement, production runtime, deployment, release, Pages or
protected-ref movement is admitted by this plan.
