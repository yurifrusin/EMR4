# Reception One authenticated Word Online dialog check plan

Date: 2026-07-31

Owner: Yuri / GPT Sol

Status: `active`

## 1. Authority and purpose

Yuri authorised the next recommended Hybrid increment: a supervised,
provider-free check of the accepted compact Reception One companion in an
already authenticated Word Online session.

This descendant may:

- use one new blank Word Online document created for the check;
- temporarily sideload a repository-local development manifest;
- serve the add-in and native Diary from the existing HTTPS loopback
  development origin; and
- submit one short authored-synthetic receptionist request through the
  accepted typed Word-to-Diary exchange.

It may not inspect document contents, Office credentials, cookies, session
storage, unrelated browser tabs or account identifiers. It grants no provider,
backend, database, appointment, command, product-data, deployment, tenant,
catalogue, IAM or release authority.

Historical Continuity nodes and consumed ledgers remain unchanged.

## 2. Exact exercise

The supervised path is:

1. open a new blank Word Online document in the user's existing authenticated
   browser session;
2. sideload a task-specific local manifest whose taskpane source contains the
   exact default-off `reception_one_companion_demo=true` capability;
3. open the EMR taskpane without reading or writing the Word document body;
4. enter one bounded authored-synthetic request;
5. open the native Diary as an Office dialog on the same
   `https://localhost:3000` origin;
6. load only the authored-synthetic smoke Diary;
7. observe the deterministic projection and exact generic return summary; and
8. close the dialog and verify focus can return to Word.

No provider or provider fallback is available. The request is view-only and
all appointment, command and provider authority remains false.

## 3. Transport and data contract

- Office authentication is used only to host Word Online. The test does not
  inspect, copy or persist Office authentication material.
- The add-in's existing application token message remains separate from the
  zero-authority launch context and the authored-synthetic companion request.
- A null or absent application token is not upgraded or repaired by login;
  the smoke Diary must remain usable without backend authentication.
- The first dialog page and taskpane share the exact HTTPS loopback origin.
- The dialog URL may contain only the non-sensitive local capability flags
  `reception_one_companion_demo=true` and `smoke=true`.
- Request text, correlation identifiers, account identifiers, document
  identifiers and tokens must not appear in the dialog URL or durable evidence.
- The existing exact request and summary schemas remain unchanged.

## 4. Acceptance gates

### Gate A - rehydration and revision binding

- Read AGENTS.md, the active Word/Hybrid/Bureau/API Spine materials and restore
  protected-evidence and user-decision boundaries.
- Verify HEAD, master, handoff/current, origin/master, origin/handoff/current
  and preserve every unrelated worktree change.
- Generate a passing five-source Ariadne receipt.
- Increment Continuity and Compass together for durable programme-state
  changes; validate exact revision binding and the rendered Compass report.

### Gate B - safe Word document

- Use a newly created blank Word Online document or independently prove an
  existing document is authored-synthetic without reading its body.
- Do not load, search, insert, replace or otherwise inspect document content.
- Do not record the Word URL, document id, tenant id, account id or filename.

### Gate C - local development manifest and origin

- Keep the canonical manifest unchanged.
- Validate a task-specific manifest with a fresh disposable development
  product id and an exact loopback taskpane URL carrying the default-off
  capability. The fresh id prevents Word from silently reusing a cached
  installed EMR add-in; it grants no tenant, catalogue or deployment identity.
- Use the existing trusted HTTPS development certificate; do not install,
  replace or trust a new certificate without user intervention.
- Make no tenant catalogue, central deployment or production change.
- The Office dialog must start on `https://localhost:3000`.

### Gate D - authored-synthetic isolation

- The companion dialog URL must include `smoke=true`.
- The Diary must label its evidence
  `authored_synthetic_client_fixture`.
- No backend, database, provider, credential, appointment command or write
  request may occur.
- Any unexpected non-Office external host, backend call or real/product-derived
  context fails the exercise closed.

### Gate E - typed exchange

- Message order remains auth, launch context, companion request.
- Launch and request correlation/date bindings match exactly.
- The native Diary verifies the requested date before interpreting the
  request.
- The deterministic proofreader releases only the existing closed generic
  summary.
- Word independently validates the summary and derives visible copy locally.
- Request text and detailed appointment data remain in the Diary.

### Gate F - real-host behavior

- Word Online loads the repository-local taskpane in the existing authenticated
  browser session.
- The Office dialog opens or produces a bounded, candid platform/policy error.
- The user gesture, popup/allow behavior, message exchange, dialog close and
  focus restoration are observed without browser automation reading unrelated
  content.
- Any interactive login, tenant policy change, add-in catalogue change or
  deployment requirement stops for Yuri's intervention.

### Gate G - verification and cleanup

- Run manifest validation, focused companion/Hybrid/Bureau/API Spine tests,
  repository-only Ariadne verification, JSON/schema validation, Python and
  JavaScript checks and `git diff --check`.
- Preserve bounded screenshots/evidence with no Office identifiers or raw
  request.
- Stop only task-owned development/debug processes.
- Check task-owned listener, browser, container and temporary-file residue.

## 5. Candid evidence limit

A pass proves only that the accepted provider-free typed companion exchange
works in one authenticated Word Online development session against the local
authored-synthetic Diary. It does not prove live backend authorization,
provider interpretation, safety for real/product-derived/patient/health data,
representative usability, cross-tenant behavior, production fitness,
deployment or release readiness.
