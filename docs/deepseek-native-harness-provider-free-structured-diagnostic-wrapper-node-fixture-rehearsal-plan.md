## Starting fact

The accepted source-static recovery proves that the generated wrapper has one
rejected entrypoint import, one exclusive sidecar writer and one identical-
value rethrow. It does not prove that Node executes those mechanics, that the
emitted JSON is accepted by the Python reader, that a failed `wx` write leaves
the original rejection in control, or that all disposable files are removed.

The native Harness remains closed. This rehearsal must not import any installed
DSH file or launch Harness, a broker, worker, model or provider.

## Narrow execution contract

One Python controller may resolve the local Node executable and create an exact
operation-owned disposable parent. It may run at most four serial Node
processes. Each process imports an authored observer, which imports the exact
generated wrapper, which imports only an authored `fixture-package/lib/bin.js`
inside that scenario root.

The observer may retain only:

- a fixed schema and scenario identifier;
- whether the caught rejection is the identical JavaScript object stored by
  the authored fixture before it throws;
- whether a rejection was caught; and
- a fixed observer exit coordinate.

It must not retain an error message, stack, path, environment, module content
or arbitrary thrown property.

## Four authored scenarios

1. `nested_known`: a `TypeError` causes an `Error` with admitted source-message
   and Node-code coordinates. The canonical sidecar must validate and identity
   comparison must be true.
2. `unknown_secret_shaped`: a newly authored secret/path-shaped message must
   collapse to `unknown` / `none`; none of its dynamic bytes may enter retained
   evidence.
3. `aggregate_multiple`: an authored `AggregateError` with two inert child
   errors must retain only `aggregate_error` / `multiple`.
4. `preexisting_sidecar`: the diagnostic path is pre-created with an authored
   sentinel. `wx` must not overwrite it, no diagnostic may be accepted, and the
   identical rejection must still reach the observer.

Each fixture and observer source is generated from fixed repository-owned
templates. The controller records their SHA-256 digests, never their dynamic
process streams. It validates safe artifacts before destroying the exact
scenario root. All four roots and the operation parent must be absent at the
terminal readback.

## Bounded correction

If the first exact candidate proves that actual wrapper JSON is semantically
safe but fails the existing canonical-byte reader solely because JavaScript
object insertion order differs from Python `sort_keys=True`, Sol may add one
recursive deterministic key-sorting serializer inside the generated wrapper.
That correction may change no diagnostic key, enum, cause traversal, write
mode, import target, rethrow, terminal relationship or authority boundary. A
new exact source commit and a fresh four-scenario run are required; the failed
run remains immutable evidence.

Any other failure stops execution for diagnosis and a newly frozen recovery.

## Acceptance

Acceptance requires:

- Node executable identity and version are captured without invoking DSH;
- exactly four serial Node processes run and all import targets remain inside
  their exact authored scenario roots;
- three safe sidecars validate byte-canonically and the pre-existing fourth is
  unchanged and rejected as diagnostic evidence;
- all four observers report caught and identical rejection;
- retained evidence contains no authored secret sentinel, stderr/stdout,
  message, stack, path or environment value;
- Node/Harness/broker/worker/model/provider counts are exactly
  `4/0/0/0/0/0`;
- all scenario roots and the operation root are absent at terminal readback;
- exact focused tests, Ruff, Python compilation and `git diff --check` pass;
  and
- accepted v1/v2 terminal and attempt-003 evidence remain unchanged.
