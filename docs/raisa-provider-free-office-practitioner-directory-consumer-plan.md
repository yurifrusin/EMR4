# Raisa provider-free Office practitioner-directory consumer plan

Date: 2026-08-02

Status: authorised implementation and acceptance contract

Parent: `provider_free_session_practitioner_directory_read_bridge_pass`

## Outcome sought

Prove that one supervised Office taskpane can consume the accepted default-off
application-session practitioner-directory factory without opening a general
product endpoint. Each tested Word surface receives one independently created
authored-synthetic application session, performs the exact active-only GraphQL
read after a visible user gesture, renders only the five display-safe fields,
then logs out and proves the session is no longer usable.

## Authority

Yuri authorised this next safe tranche and five further clear provider-free
descendants, selecting Sol's recommended direction at non-material forks. This
tranche may add one task-scoped harness, two fresh development manifests,
authored-synthetic UI assets, deterministic tests, sanitized evidence,
continuity, documentation and task-branch publication.

It may not mount the factory in `app.main`, use live Microsoft or another
provider, map a real identity, inspect Office account or document content,
read patient or clinical data, add another product resource, issue a product
command, write product truth, deploy, rebuild Pages, decide Dependabot alert
17, move a protected ref or read/include `docs/branding/`.

## Frozen contract

1. The harness is a separate explicitly constructed FastAPI application. It
   mounts the existing application-auth logout route and two surface-bound
   instances of the accepted GraphQL factory; the product composition root is
   unchanged.
2. Installed Word and Word Online use independent authored-synthetic practices,
   principals, sessions, CSRF values, result nonces and cookie partitions.
3. The no-store taskpane response sets only the accepted Secure, HttpOnly,
   SameSite=None, Partitioned `__Host-` application-session and CSRF cookies.
   The matching CSRF value is held only in taskpane memory and removed after
   logout.
4. Office host admission must match the manifest-bound `word_desktop` or
   `word_online` surface before the button is enabled or any product request is
   sent.
5. One visible button sends JSON POST with `credentials: include`, exact origin,
   in-memory CSRF header and one fixed `Directory` operation. The variables are
   exactly `activeOnly=true`, `limit=200`, `offset=0`; the client cannot select
   practice, role, policy, resource, fields or operation.
6. The client accepts only `data.practice.practitioners`, exactly two rows for
   acceptance, and exactly `id`, `displayName`, `roleLabel`, `active`, and
   `defaultLocation { id name }`. Every row must be active. Projection drift,
   GraphQL errors, HTTP failure, host mismatch or malformed data fails closed.
7. The user sees authored-synthetic display names and optional role/location
   only. Raw GraphQL errors, endpoint names, identifiers in durable evidence,
   cookie/CSRF/session values, database targets and Office identity never enter
   user copy or committed evidence.
8. A successful render is followed by the accepted authenticated logout REST
   command and one direct backend validation that the same surface session is
   rejected. A read without successful logout is not an accepted terminal pass.
9. Application-auth and product database authority retain the accepted separate
   finite NOINHERIT LOGIN/capability pairs. Product access remains exact-column
   read-only and application-auth audit remains required before release.
10. The database, four task roles, product rows, sessions, server, listener,
    relay and developer registration are disposable and must be absent or
    stopped at closeout.

  `2e34bdad732fdab32fbf778280b3d3c70d66d602`.
- Static tests prove exact query, projection, host/surface binding, no-store
  headers, CSP, one delivery per surface, closed result schema, user-safe error
  copy and absence of document/provider/patient/clinical/write APIs.
- Real loopback HTTP and disposable PostgreSQL prove two independently scoped
  exact reads, two committed authorization-allowed audits, logout/revocation,
  post-logout denial, direct role denials and complete cleanup.
- Rendered browser evidence exercises load, visible button, exact two-row result,
  logout terminal state, keyboard focus and narrow taskpane layout. Any Office
  runtime stub is labelled route-intercepted and is not called real Office.
- Supervised installed Word and Word Online each pass before a cross-host result
  is claimed. A host blocked by external policy is reported separately and is
  not replaced by a browser-stub result.
- Focused and inherited API Spine, GraphQL, application-auth, Office, security,
  manifest and continuity tests pass, with existing repository barriers reported
  exactly rather than overridden.

## Claim limit and handoff

A pass proves only two supervised authored-synthetic Office renders of one
active-practitioner read through one exact development origin and the accepted
local application-session/PostgreSQL boundary. It establishes no real identity,
patient or clinical safety, document access, general endpoint mounting, broader
product read, product write, distributed abuse resistance, organisational
Office deployment, production, release or public branding decision.
