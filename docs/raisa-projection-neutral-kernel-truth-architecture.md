## Invariant

A Raisa modality is a renderer of authorised meaning, not an owner of that
meaning. It may select, compress, arrange, describe and request. The kernel
alone establishes principal and practice scope, current source truth, command
admission, confirmation meaning, atomic result, audit and receipt.

Two renderers have truth parity for a command family when their normalized
kernel traces agree for the same selected-current coordinate and outcome. They
do not need the same layout, wording, focus order, history model or device.
Truth parity therefore does not imply feature parity.

## Current proved instance

For the existing appointment-status family, the conventional grid and
Reception One both converge on the existing `setAppointmentStatus`
proposal/confirm interaction and its fresh-truth reconciliation. Twelve
route-intercepted browser traces cover safe, cancelled, blocked, stale, failed
and committed outcomes. All six renderer pairs agree on every frozen kernel
field, and no raw compatibility write is used.

## Future modality admission

A future visual, conversational, email, SMS, thin-web, voice or delegated-bot
renderer may reuse this pattern only after its own exact identity, privacy,
transport and command boundary is authorised. Its local grammar may differ,
but it must:

1. address the same current authorised domain coordinate;
2. submit intent to the same command-family kernel;
3. preserve proposal and confirmation meaning;
4. treat cancellation, blocking, staleness and failure as no-commit outcomes;
5. display a committed terminal state only from authoritative reconciliation;
6. provide no raw fallback or renderer-owned command path; and
7. keep renderer-local state outside source truth, audit and receipt authority.

The repository `ProjectionTruthTrace` is test evidence for these rules. It is
not a transport protocol, runtime context object, product event, audit record,
database model, analytics schema or patient transcript.

## Boundary

This architecture does not authorise another renderer, command or event
family; a patient channel; identity or recovery design; product data; backend,
database or watcher runtime; provider use; deployment; production or release.
