## Frozen risk classification

One exact typed tranche profile declares change domains and risk signals. The
deterministic classifier selects the highest applicable tier; callers cannot
choose or lower their own tier.

- `tier_0_metadata`: documentation, receipt metadata, continuity metadata or
  error-register packaging only, with no executable, product, policy, security
  or authority change.
- `tier_1_provider_free_source`: provider-free, unmounted harness/product source
  or test work with no database runtime, authority/security boundary, command,
  real/product data, provider, deployment or protected-ref effect.
- `tier_2_authority_runtime`: migration representation or execution, database
  runtime, product command/write, authority/security contract, executable tool,
  network capability or operational product-derived data.
- `tier_3_occupied_protected`: patient/clinical or other real-person data,
  occupied provider call, credentials/IAM, deployment/production/release,
  Pages or protected-ref movement.

Contradictory `docs_only` or `unmounted` claims fail closed. Every tier inherits
the five-source, protected-evidence, explicit authority/data/effect/cleanup,
immutable-failure, exact candidate/worktree, explicit-path staging, latch and
protected-ref controls. Risk weighting may remove duplicate evidence work; it
may never remove a hard control.

## Baseline-first and semantic freeze

- Tier 1 through Tier 3 require an exact canonical baseline fingerprint and
  result captured before the first semantic edit. Known failures are named by
  stable IDs; rediscovery later is not a candidate regression.
- Tier 0 requires only its targeted baseline unless it changes an admitted
  workflow policy, in which case classification rises.
- One semantic freeze records exact source HEAD/tree, semantic-binding digest,
  toolchain digest and focused-gate results.
- The canonical full profile runs once after semantic freeze. It is not rerun
  for later closeout prose, receipt, continuity, error-register revision or
  mailbox-only changes while those changes leave all semantic bindings intact.
- An exact unchanged pass/failure/uncertain result continues to use the accepted
  continuity gate: reuse exact pass, diagnose without rerun, or resolve
  uncertainty; no stale result becomes success.

## Change-triggered rerun matrix

The typed profile and result use closed change families. The deterministic
decision must return at least these requirements:

| Post-freeze change family | Required rerun |
|---|---|
| product, harness, policy, schema, migration or semantic test | focused semantic gates plus one canonical final profile; invalidate earlier verifier result |
| verifier command manifest | manifest validation and exact verifier-worktree/path preflight; no product canonical rerun by itself |
| documentation or closeout prose only | document metadata/link/whitespace checks only |
| Continuity, Compass or baton metadata only | exact continuity/Compass/baton tests only |
| receipt/runtime-state only | exact receipt/preflight tests only |
| agent-error register only | register/schema/pattern tests only |

Mixed changes take the union. Unknown or falsely narrowed classes fail closed.
A recorded canonical pass may be reused only when semantic HEAD/tree, semantic
bindings, relevant inputs and toolchain remain exact.

## Review economy

- One deterministic semantic gate precedes every external reviewer.
- Tier 0 has no external veto unless a named ambiguity or policy/security
  trigger raises the tier.
- Tier 1 has no routine veto. One veto is required only for a new authority or
  security boundary, prior substantive rejection, ambiguous hard boundary or
  other explicit risk trigger.
- Tier 2 and Tier 3 require exactly one final independent veto after
  deterministic admission.
- Planning, formatting and intermediate mechanical corrections do not receive
  separate external reviews. A substantive rejection enters one bounded
  recovery and may receive one new final veto; concurrent or stacked reviewers
  are inadmissible.

This tranche is `tier_2_authority_runtime` because it changes workflow admission
and reviewer authority policy, despite being provider-free and repository-only.

## Stable semantic bindings

Semantic bindings may contain only source, contract, policy, schema and
semantic-test paths that affect the claim. Receipt files, timestamps, current
latch snapshots, generated closeouts, mailbox messages and current-baton prose
are volatile evidence and cannot be hashed into product semantic contracts.
They remain independently validated by their targeted gates. A semantic path
and a volatile path may not be duplicated or reclassified by the caller.

## Named threats, incidents and tail work

- Acceptance names threat IDs and the deterministic gate IDs covering them.
  Every required threat must have coverage, but numeric mutation quotas are
  advisory only and cannot substitute for coverage.
- A qualifying incident receives one minimal typed machine record before a
  corrected attempt. Full narrative revision documents and aggregate pattern
  regeneration may be batched at closeout. Several symptoms with one
  origin/category/role/resource/signature are one causal incident; distinct
  origins remain distinct.
- A tail item may be deferred only when both `safety_relevant` and
  `authority_relevant` are false and an owner plus next review boundary are
  named. Integrity, privacy, atomicity, authority, protected-evidence or
  irreversible-effect defects are never timeboxed away.

## Verifier-worktree correction

The serial pytest launcher gains an explicit `--repo-root` option. It defaults
to its current repository root for compatibility, but a verifier using a
launcher outside the candidate worktree must bind `--repo-root` to the exact
candidate worktree. The value must resolve to a repository containing the
expected test conftest; relative candidate paths then resolve there.

Verifier preflight may accept an exact v1 command manifest and must validate
before dispatch that:

- every command ID/argv passes the existing manifest validator;
- every declared repository path exists with its required file/directory kind;
- candidate paths resolve inside the exact review worktree;
- an external serial-pytest runner has an exact `--repo-root` equal to that
  worktree; and
- no relative candidate test path is admitted behind a runner rooted in a
  different checkout.

Shared interpreter and explicitly allowlisted tool paths may remain outside the
candidate worktree. No command is executed by preflight.
