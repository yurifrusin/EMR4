## Outcome

Increment 1 establishes a working, local and metadata-only continuity layer
without changing or pausing the Reception One product surface. It is more than
a branch diagram: it records directed multi-parent lineage, inherited product
contracts, globally closed authority boundaries, repository evidence pointers,
candidate knowledge harvests and explicit branch dispositions.

The repository now contains:

- a valid Codex plugin and reusable `ariadne-continuity` skill;
- a standard-library command-line engine supporting `validate`, `audit`,
  `show`, `checkpoint`, `fork`, `harvest`, `compare` and `close`;
- a JSON Schema and a canonical six-node EMR4/Reception One seed graph;
- deterministic validation, inheritance, safety and mutation tests; and
- a machine-readable Increment 1 evidence summary.

The plugin is deliberately not installed into a personal or repository
marketplace. No MCP server, thread hook, visual map or automatic Git/task action
was added.

## First useful continuity result

The canonical chain is:

`Stage 1 combined intent → meta-grid concept → functional client → live-local integration → Reception One review`

behaviour contracts and does not displace the active review.

patient, practitioner, duration and bounded time must be exercisable together,

functional-client and live-local nodes remain historically `accepted` for their

- `contract_gap_open:meta-grid-live-local-integration:combined-patient-practitioner-time-duration-intent`.

increment would be a read-only pre-plan continuity packet: given a proposed
tranche node, compute its ancestors, inherited contracts, candidate harvests,
closed boundaries and unresolved evidence into a compact human-review artifact.

without hooks that can silently change task or Git state.

for the combined patient/practitioner/duration/time request. This Increment 1

thread integration, marketplace installation, transcript import and multi-model
