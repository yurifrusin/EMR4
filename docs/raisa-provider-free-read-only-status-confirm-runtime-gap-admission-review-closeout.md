## Blocking gaps

1. The route claims and locks idempotency before loading the appointment; it
   does not lock practice, appointment and idempotency in the accepted order.
2. Active-user and role checks occur before the handler, with no server-session
   binding or in-transaction current-authority recheck after waits.
3. The confirmation route accepts both status and waiting-area inputs rather
   than discriminating the status kernel before request construction.
4. A terminal re-transition is currently a warning, not a fail-closed
   `transition_policy_deferred` result.
5. Proposal and submitted warning codes are concatenated instead of compared as
   an exact duplicate-free set.
6. Status mutation, audit and completed receipt are staged before one commit,
   but the durable status receipt does not retain the audit identifier.
7. Stored replay may be disclosed before target locking and the required
   in-transaction current-authority recheck.

## Partial gaps and useful foundation

- Signed evidence already binds practice, actor, command, current state and
  freshness, but not a server session or durable locked source version.
- The idempotency service stores canonical response JSON and a digest and
  replays the stored JSON, but initial delivery uses a separately held response
  object and there is no explicit unknown-commit delivery contract.
- Appointment mutation, attributable audit and completed response are already
  staged before one transaction commit. The convergence design should preserve
  that foundation rather than replace it.
