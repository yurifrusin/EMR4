## Plan Summary

Introduce ONE evidence-gated appointment-UPDATE confirm endpoint (POST /api/v1/appointments/proposals/update/confirm) that both the human diary-edit path and Bernie tool-intent extension path write through, mirroring the existing create confirm-bernie grammar: proposal -> evidence/staleness/signed/session-binding gate -> exactly one write + one bounded audit-evidence trail. Bernie-authored updates can then no longer commit via the raw PUT /{id} bypass; the human UI keeps PUT for backward compatibility this sprint but gains the same confirm route as its deterministic path.

## My Understanding

Today CREATE has a rich confirm grammar (POST proposals/create/confirm-bernie): it revalidates a supervised proposal, enforces confirmed=true, verifies HMAC signed_confirmation_evidence, runs candidate/proposal freshness staleness gates (bernie_turn_evidence.py), validates optional server session binding, then writes exactly one appointment plus a bounded audit_evidence list. UPDATE has no such confirm layer. propose_update_appointment (POST proposals/update/{id}) is a non-mutating proposal, and both the human diary editor (diary.js ~7621 then PUT ~7659) and Bernie tool-intent (propose_bernie_tool_intent at router 1300, which internally calls propose_update_appointment; diary.js confirm at 1621 -> PUT 1634) commit through the same raw PUT /{id} (update_appointment, router 3025) carrying only confirmed_warnings. So a Bernie-influenced extension reaches the diary write with none of the confirm-grade evidence gating (signed evidence, freshness/staleness, session binding) that the create path mandates. G1 removes that asymmetry: add a single deterministic update proposal/confirm/write grammar, route Bernie tool-intent writes through it (signed evidence required), and forbid the raw-PUT bypass for Bernie-authored updates while leaving direct human PUT edits working.

## Intended Surface / Boundary

Backend only for the core: app/routers/appointments.py (new confirm-update endpoint + shared update-apply helper extracted from update_appointment + tool-intent minting of confirm envelope), app/schemas/appointments.py (new BernieUpdateProposalConfirmationIn / AppointmentConfirmUpdateProposalOut, extend BernieToolIntentOut with confirm envelope + freshness id), app/services/bernie_turn_evidence.py (add update-scoped signed-evidence purpose constant + update signed-payload helper; reuse compute_proposal_freshness_id/check_staleness). Focused tests under tests/. ## Risks / Ambiguities

A) Re-evaluating via propose_update_appointment must reconstruct the same incoming field set from the confirmed command; if reconstruction drifts from the command the gate could pass a different change than shown - mitigate by driving both proposal and confirm from AppointmentUpdateCommand fields and asserting equality of the recomputed command. B) update lacks a selected_candidate, so freshness is computed only from the update command (compute_proposal_freshness_id) - acceptable but means candidate-level staleness is not applicable; document that. C) Keeping raw PUT for humans means the asymmetry is only fully closed for Bernie this sprint; a later sprint could route the human UI through the confirm endpoint too - flagged as intentional incremental scope. D) Signed-evidence purpose separation is essential so create evidence cannot confirm an update; covered by an explicit wrong-purpose test. E) diary.js is a visually adjacent surface - change is limited to the confirm networking call, no layout/markup change; smoke harness guards regressions. F) Alternative considered: a single generic diary-action confirm endpoint for all mutations - rejected as out-of-scope/riskier; update/extend first keeps the grammar deterministic and reviewable.
