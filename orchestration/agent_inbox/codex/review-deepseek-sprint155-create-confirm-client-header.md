## Review Questions

### 1. Should staff create-confirm reuse the modal create-proposal key or use a separate key?

**Use a separate key.** The modal `saveBtn.dataset.idempotencyKey` is generated by `generateClientIdempotencyKey()` for the create-proposal POST (`/proposals/create`). Both create-proposal and create-confirm hit different backend `operation_id`/`route_family` values, so reusing the same key across the two hops would cause the backend to create an entirely separate ledger entry (key collisions are impossible because `claim_appointment_command` scopes on `(practice_id, actor_user_id, operation_id, idempotency_key_hash)` — the `operation_id` is `confirmAppointmentCreateProposal` for the confirm route vs something different for the create-proposal route). So reuse would not cause a backend conflict. The problem is **semantic and lifecycle safety**:

- **Replay scope**: If the proposal key is reused for the confirm and a retry happens after modal reset (`resetProposalConfirmation()` clears `saveBtn.dataset.idempotencyKey`), the confirm retry would regenerate a new key, losing the replay benefit. A confirm-scoped key should survive independent of modal-proposal state.
- **Staleness ambiguity**: The backend’s `stale_after` (10 minutes) starts from the first claim. If the proposal key was generated minutes earlier for proposal eval, a confirm retry might find it stale before the confirm even gets a chance to complete.
- **Same-key confusion**: The same string representing two distinct operations makes debugging and ledger auditing harder. A future developer inspecting the ledger cannot tell whether a replay belongs to proposal re-evaluation or confirm retry.

**Recommended separation**: Add a `confirmIdempotencyKey` scoped to the confirm lifecycle. Generate it when the confirm payload is assembled (after proposal response arrives), store it on the `saveBtn` dataset or a new shared variable, and clear it when the confirm succeeds or the proposal is superseded. This gives clean replay semantics: a confirm retry uses the same key until the confirm completes or the proposal is superseded by a re-proposal.

The `getServerRouteIdempotencyKey()` method on `BernieSession` already demonstrates the per-turn, per-route key pattern the frontend could follow. A simpler approach for the modal: store the confirm key under `saveBtn.dataset.confirmIdempotencyKey`, generate on first confirm attempt, clear on proposal supersede/reset. This keeps confirm-retry stable without coupling to proposal-key lifecycle.

### 2. Which confirm-Bernie frontend surfaces should be covered in Sprint 155, and which should be deferred?

**Cover in Sprint 155:**

1. **`saveBooking` staff create-confirm path** (line ~7571): This is the nearest runtime break after Sprint 153. The booking modal generates a proposal successfully and the backend accepts it, but the immediate confirm hop fails with `400 Idempotency-Key is required for confirming appointment proposals.` Fix this first — it blocks the simplest new-appointment workflow.

2. **`saveBooking` drag/reschedule update-confirm path** (line ~8044): This is the second-commonest non-Bernie confirm surface. When a staff user drags an appointment to a new time/slot, the proposal succeeds but the confirm fails identically. This surface is inside the same `saveBooking`-adjacent function pattern and shares the same fix approach: generate a confirm key, store it on the proposal-level variable, send as header.

3. **Bernie confirm adapter pilot path** (line ~5169): This is the primary Bernie slot-selection confirm surface. The pilot adapter sends `confirm-endpoint = /proposals/create/confirm-bernie` and already has access to `bernieSession.getServerRouteIdempotencyKey()`. This is the smallest Bernie surface to fix because the session already has a key generator — just pipe it into the `Idempotency-Key` header.

**Defer to Sprint 156+:**

4. **`confirmBernieToolIntentChange()`** (line ~1734): This is a secondary Bernie confirm path for tool-intent changes (extend, duration edit). It uses the envelope’s `confirm_endpoint` which could be any of the confirm routes depending on context. Deferring this is safe because tool-intent is less commonly exercised than the primary slot-selection confirm adapter path.

5. **`applySignedStatusProposal()`** (line ~8086): Status confirm route. The status proposal workflow has its own confirmation dialog and is structurally independent of the create/update flows. Wire after create-confirm and update-confirm are stable.

6. **`applySignedDeleteProposal()`** (line ~8130): Delete confirm route. Same rationale as status confirm — separate lifecycle, wire after core create/update paths.

### 4. What risks/boundaries must remain closed?

**Do not open in Sprint 155:**

- **Backend ledger or runtime behavior**: The backend `claim_appointment_command`/`complete_appointment_command` and all six confirmed routes must not change. Sprint 155 is frontend-only header emission.

- **Raw compatibility write paths**: `POST /appointments`, `PUT /{id}`, `PATCH /{id}/status`, `DELETE /{id}` remain exempt and must not receive client-side idempotency headers (they don’t enforce them server-side and adding headers would be misleading).

- **Proposal-only routes**: `/proposals/create`, `/proposals/update/{id}`, `/proposals/status/{id}`, `/proposals/waiting-area/{id}`, `/proposals/delete/{id}` — these remain a deferred backend binding gap (Sprint 152+). No frontend header changes for these.

- **`minLength: 8` runtime enforcement**: Sprint 153 readiness guard established this precondition; Sprint 155 must not add runtime min-length validation on the backend. The frontend already generates keys that satisfy 8+ chars naturally via `crypto.randomUUID()` (36 chars) or the `evt-...` fallback.

- **Providers, GraphQL, H15/H-series, memory/RAG/GraphRAG**: All remain closed as documented in every prior Sprint closeout.

- **Status-confirm and delete-confirm routes**: The backend routes are already enforced and working, but the frontend must not wire these in Sprint 155. They remain explicitly tracked as deferred in the header inventory test.

- **Bernie session body-level idempotency keys**: The `server_session_idempotency_key` body field in Bernie envelopes must not be treated as interchangeable with the HTTP `Idempotency-Key` header. The confirmation ledger reads the header only.

- **Per-proposal confirm key as route-binding authority**: Adding a confirm-scoped key must not imply the frontend gains route-configure authority, proposal rerun authority, or the ability to confirm without staff review. The backend’s existing freshness-id and signed-evidence guards remain the sole write-authority gates.

## Adversarial Observations

### 5.1 The Bernie session already has a key generator — use it

`BernieSession.getServerRouteIdempotencyKey(kind, discriminator)` generates per-turn, server-session-scoped keys. The Bernie confirm adapter at line ~5169 and `confirmBernieToolIntentChange` at line ~1734 both have access to `bernieSession`. The simplest fix: call `bernieSession.getServerRouteIdempotencyKey("confirm", "create-confirm-bernie")` and pass the result as `headers["Idempotency-Key"]`. This avoids adding a new key-generation pattern for Bernie surfaces.

The staff confirm paths (`saveBooking`, drag/reschedule) do not have a `BernieSession` reference, so they need their own confirm-key variable as described in section 1.

### 5.2 The update-confirm endpoint is shared between two different frontend paths

The drag/reschedule path (line ~8044) and the `saveBooking` update path (line ~7508) both use `confirmEndpoint = proposal.confirm_endpoint` which resolves to `/proposals/update/confirm`. They are separate `apiFetch` call sites but share the same endpoint path. The key generation pattern should be identical — the confirm key for an update should be scoped to the same update proposal and cleared when the proposal is superseded (e.g., a new drag starts before the old one confirms).

### 5.3 The Bernie confirm adapter has wider `isConfirmAdapter` logic than strict confirm routing

The `isConfirmAdapter` boolean at line ~5132 is gated on pilot status, smoke mode, and URL parameters. It controls whether the pilot confirm button uses the real API or simulated confirmation. Sprint 155 should add the header inside the `if (isConfirmAdapter && payload.confirm_endpoint && payload.confirm_payload)` block so it only affects the real API path, not simulation.

### 5.4 The header inventory guard already tracks every call site — Sprint 155 must update it

`tests/test_api_spine_frontend_header_inventory.py` currently asserts `source.count('"Idempotency-Key"') == 1` (only the create-proposal call). If Sprint 155 wires 2-3 more sites, this count will break. The test should be updated to assert per-caller header emission rather than a global count, or the global count should be raised to the expected wiring total.

Similarly, `test_frontend_confirm_callers_are_explicitly_tracked_as_missing_headers` asserts `not _contains_idempotency_header(block)` for each wrapped block. Wired blocks should switch to `_contains_idempotency_header(block) == True` with deferred blocks remaining tracked as missing.

## Verdict

**Sprint 155 implementation is low-risk and well-scoped** if it limits itself to the three confirm surfaces identified in section 2: staff create-confirm, drag/reschedule update-confirm, and Bernie confirm adapter. The backend is already enforced and working — this is purely frontend header emission. The key-separation pattern (independent confirm key, not proposal-key reuse) gives clean replay semantics without breaking existing create-proposal behavior. The seven closed boundaries in section 4 must remain untouched.
