## Context

Sprint 153 closed the first concrete client-readiness gap by making the real
Diary create-proposal caller send an HTTP `Idempotency-Key` header. Backend
runtime `minLength: 8` enforcement remains deferred, and create-proposal
continues to use deterministic re-evaluation with no proposal ledger.

Sprint 154 maps the remaining mismatch between Diary frontend callers,
FastAPI-enforced confirmation routes, and OpenAPI proposal-command posture.

## Current Covered Caller

Exactly one Diary caller currently emits HTTP `Idempotency-Key`:

| Caller | Route | Current posture |
|---|---|---|
| `saveBooking` create-proposal branch | `POST /api/v1/appointments/proposals/create` | Wired in Sprint 153; key is stored on `btn-booking-save.dataset.idempotencyKey` and generated by `generateClientIdempotencyKey()` |

## Enforced Backend Confirm Routes Still Missing Diary Headers

These FastAPI confirmation routes already bind
`Header(None, alias="Idempotency-Key")` and fail closed when the header is
missing or blank. The Diary frontend does not yet send the header for these
confirm hops.

| Backend route | FastAPI handler | Diary caller(s) | Sprint 154 posture |
|---|---|---|---|
| `POST /api/v1/appointments/proposals/create/confirm` | `confirm_create_proposal_route` | `saveBooking` create confirm branch | Missing frontend header |
| `POST /api/v1/appointments/proposals/create/confirm-bernie` | `confirm_bernie_create_proposal` | Bernie review confirm adapter and `confirmBernieToolIntentChange` | Missing frontend header |
| `POST /api/v1/appointments/proposals/update/confirm` | `confirm_update_proposal_route` | `saveBooking` update confirm branch and drag/reschedule confirm branch | Missing frontend header |
| `POST /api/v1/appointments/proposals/status-confirm` | `confirm_status_proposal_route` | `applySignedStatusProposal` | Missing frontend header |
| `POST /api/v1/appointments/proposals/delete-confirm` | `confirm_delete_proposal_route` | `applySignedDeleteProposal` | Missing frontend header |

The Bernie session layer can carry body-level session idempotency fields such as
`server_session_idempotency_key`, but the appointment confirmation ledger reads
the HTTP `Idempotency-Key` header only. Body fields do not satisfy these
confirmation routes.

## Proposal-Only Backend Binding Gap

OpenAPI documents shared proposal-command `Idempotency-Key` parameters for the
canonical proposal operations. FastAPI currently binds the header only for
create-proposal. These proposal-only routes remain a deferred binding gap and
must not inherit confirmation replay authority by accident.

| FastAPI handler | Current route | Runtime header binding |
|---|---|---|
| `propose_update_appointment` | `POST /api/v1/appointments/proposals/update/{appointment_id}` | Not bound |
| `propose_status_update` | `POST /api/v1/appointments/proposals/status/{appointment_id}` | Not bound |
| `propose_waiting_area_update` | `POST /api/v1/appointments/proposals/waiting-area/{appointment_id}` | Not bound |
| `propose_delete_appointment` | `POST /api/v1/appointments/proposals/delete/{appointment_id}` | Not bound |

## Deferred Surfaces

Sprint 154 does not change:

- raw compatibility `POST /appointments`, `PUT /appointments/{id}`,
  `PATCH /appointments/{id}/status`, or `DELETE /appointments/{id}`;
- slot-search reservation or replay semantics;
- Bernie interpreter/session command idempotency expansion;
- OpenAPI `minLength: 8` runtime enforcement;
- provider calls;
- GraphQL mutations;
- H15/H-series runtime imports;
- memory/RAG/GraphRAG runtime wiring;
- broad historical diary trove mining.

## Sprint 155 Recommendation

Sprint 155 should wire the create-confirm client header path first:

1. staff create confirm from the booking modal;
2. Bernie create confirm from the Bernie review/confirm surfaces.

This is the nearest runtime break after Sprint 153 because create-proposal now
prepares evidence successfully, but the immediate confirm hops already require
an HTTP `Idempotency-Key`. The slice is smaller than wiring all confirm
families and safer than starting with broader proposal-only backend binding.

Status-confirm, update-confirm, delete-confirm, proposal-only header binding,
and strict `minLength: 8` runtime enforcement should follow in later bounded
sprints.
