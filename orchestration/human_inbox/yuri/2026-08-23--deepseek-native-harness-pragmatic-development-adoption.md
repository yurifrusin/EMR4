# DeepSeek native Harness pragmatic development adoption

Date: 2026-08-23

Timestamp: 2026-08-23T09:22:37.2550535+10:00 (Australia/Brisbane)

## Lay summary

The conclusion is that we have tested the native Harness enough to start using
it for real development work. It is not yet the default, but it no longer sits
behind another ceremonial test programme.

What it has clearly earned is trust in its instrumentation: when it fails, we
can usually tell where, after which request, with which tool result, whether any
file changed, and whether it cleaned up. What it has not earned yet is a claim
that it completes useful work more reliably than DeepSeek through Claude Code.
The only sensible way to answer that now is to give it real bounded work.

The earlier boot obstacle has in fact been solved. We will not repeat it. We
will also stop limiting a coding agent to one model request when ordinary
self-correction often needs a read, an edit error, another read and a corrected
edit.

## First real work

The next tranche gives the native Harness one small but genuine EMR4 task: the
unmounted, non-secret canonical check-in environment-manifest normalizer and
its tests. It is real repository development while remaining unable to access
configuration, secrets, databases, routes, product data or ordinary-practice
activation.

If it fails after seeing the work packet, we will not begin another long
Harness-internals investigation. We preserve the trace, recover the task
elsewhere and try the native worker later on a different bounded assignment.

## Workflow reading

Ten cheap local evidence/closeout-command mistakes occurred while assembling the
review. All were syntax, path or display-shaping errors and none caused a model,
runtime, product or protected rerun; the ninth was a clockwork-rejected
multi-parent Continuity node. This is useful confirmation of the new
direction: the clockwork should take sparse boundary readings, not wrap every
small action in more procedure.
